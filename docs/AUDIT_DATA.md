# SAFECheck 2.13.0 data and identity audit

Reviewed the 2.12.0 baseline and final 2.13.0 changes in the models, repository, core and administrative services, SCAM supplementation, reputation/report moderation, group outboxes, legacy importer and Alembic revisions `0001`–`0009`. This review used source inspection and synthetic test identities. It did not query or modify the running bot's database, inspect private backup contents or expose credentials.

## Findings and resolution

| Finding | Final behavior and evidence |
| --- | --- |
| An unknown-ID SCAM record could be bound to a different numeric ID while another observed numeric account already owned its username. This could create competing current username metadata and an inappropriate ban outbox entry. | The current numeric owner is checked inside the shared identity transaction before binding. Both a fresh requested ID and an existing ID without a username are rejected when they conflict. SQLite and isolated PostgreSQL regressions verify that the record, original identity, audit and ban outbox remain unchanged. |
| A known numeric account sharing a username with an unresolved SCAM record could receive a clear lookup result, even though the same match excluded it from TRUSTED and TOP. | The service returns a separate unresolved username match. LT/EN/RU cards explain that the username matches an unresolved record and its link to this numeric ID is unconfirmed. This neither marks the numeric account as confirmed SCAM nor creates a ban. Regressions cover the three languages, rename/removal of the match and precedence of a directly confirmed numeric record. |
| Some administrative mutations checked authority before waiting for a transaction lock, allowing a revoked administrator to finish later. | Coordinated with the security review. Final mutations serialize with administrator changes and recheck authority after acquiring the shared lock. The security regressions and a real PostgreSQL lock-wait case cover the correction. |

An explicitly confirmed matching numeric owner remains a valid binding. The new matching-owner regression verifies that only the selected SCAM record moves: its reference, creation time and moderator remain; historical reputation and reports stay attached to their original user row. No user rows are deleted or merged. The SQLite timestamp comparison normalizes its timezone representation; it does not change stored timestamps.

## Transaction and schema review

Numeric Telegram ID remains the durable identity. Observed usernames are mutable metadata, normalized by the application and retained in history. The shared identity lock serializes ownership observations, administrative identity supplements and authority changes. SCAM supplementation commits the record change, audit event and approved-group ban outbox together; rollback and nonce replay are covered by the existing suite. Numeric uniqueness, active-SCAM uniqueness, reputation-pair uniqueness and request-key uniqueness remain enforced by the database. No historical REP, report or moderation records are automatically transferred because usernames match.

Reputation requests affect totals only after approval. Repository totals use one ledger query across legacy events, approved requests and compensating adjustments. Per-user operation locks coordinate competing reputation decisions and resets. Report approvals preserve the original report and add immutable moderation/audit records; repeated matching decisions do not add another active SCAM record. Outboxes use unique activation/recipient keys and recheck eligibility before external delivery. These controls do not make external Telegram calls transactionally atomic with database commits.

The release needs **no new migration** and retains Alembic head **`0009`**. The actual migration tests, included in the final suite, verify upgrade to head, model/schema agreement, downgrade to base and re-upgrade on disposable SQLite databases. Historical-data cases preserve legacy reputation, users, reports, SCAM records, audit events, member/recovery data and administrator records across the relevant revisions. Revision `0009` preserves legacy pending requests with a nullable comment and retains value, status and self-vote constraints through SQLite batch alteration. New service submissions still require validated comments. Downgrading below `0009` drops comments and must not be treated as a lossless production rollback after new comments exist.

## Verification and limits

The integration owner completed the final Docker suite: **569 passed in 111.52 seconds**, including the new data cases on SQLite and isolated PostgreSQL schemas, existing PostgreSQL concurrency contracts, Redis isolation and migration tests. The operations review also exercised backup and restore using separate QA services. These executions did not insert test records into the live bot's database. `tests/test_final_data.py` contains the independently authored ownership-conflict and matching-owner preservation cases.

No unresolved release blocker remains in this review's scope. Telegram does not verify arbitrary username/ID ownership; an administrator must independently establish that link before confirming a supplement. Tests do not establish real-user evidence delivery, future host uptime, an actual VPS reboot, configured offsite storage or disaster recovery from that storage. Final candidate deployment was pending when this audit was written; its outcome belongs in the release record. This review provides no assurance about live data integrity beyond the migration and isolated verification evidence stated above.
